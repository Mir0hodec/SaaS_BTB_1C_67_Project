# ИИ-помощник ГК «Эксперт» в 1С-Коннект

Как бот из презентации «Claude в Телеграме», только канал — 1С-Коннект.
Сотрудник пишет учётной записи «ГК Эксперт | ИИ-помощник» в разделе «Коллеги»
обычным языком и получает ответ в тот же личный чат — из живой базы 1С или
из базы знаний компании.

```
Сотрудник → личный чат 1С-Коннект → приложение 1С-Коннект (учётка бота) → connect_adapter → очередь
         → Claude Code (Opus 5, high) → MCP → база 1С / база знаний
         ← ответ и файлы: REST SendMessagecolleague / SendFileСollegue
```

## Личные сообщения: как устроено и почему так

- **Ответы** — официальный REST: `POST /v1/colleague/send/message/` (JSON, Basic Auth), файлы — `/v1/colleague/send/file/`.
- **Приём.** Push-событий для личных чатов в API 1С-Коннект нет: вебхук `SetHook` бывает только `bot` и `line`, то есть по линиям поддержки. SOAP `GetHistoryOfColleaguesChat` отдаёт HTML-архив переписки пары сотрудников с лимитом 100 вызовов в час — для диалога не годится. Мгновенно получать сообщения можно только через «API приложений»: событие `Mode="Colleagues" Object="Message"` от десктопного приложения 1С-Коннект, запущенного на сервере под учёткой бота. В документации этот способ помечен как устаревший. Подробно, с запросом разработчикам 1С-Коннект — в [docs/Техническое заключение 1С-Коннект.docx](docs/).
- **Транспорт** — `bridge/connect_adapter.py`. Любой источник приводится к одному JSON-контракту (`message_id, sender_id, recipient_id, text, timestamp`), поэтому заменить источник — одна строка. Есть HTTP-приёмник `POST /connect/colleague/message` с Bearer-токеном: для проверки и под будущий push-механизм.
- **Защита:** дубли отсекаются по `message_id`, свои сообщения бота и эхо игнорируются. У каждого сотрудника своя сессия — истории не смешиваются. Ошибки доставки попадают в журнал. Канал переподключается сам.
- `SetHook` и линии в этом режиме не вызываются, так что действующие интеграции Коннекта не затрагиваются. Режим линии поддержки с вебхуком остался: `connect.channel: line`.

Проверка по шагам с фактическими HTTP-кодами — `scripts/connect_check.py` (`auth`, `send`, `pipe`, `inbound`).

## Что умеет

| | |
|---|---|
| Вопросы по данным | `#демо остатки по кассе на 1 сентября` — база выбирается хэштегом, опечатки прощаются |
| Помнит разговор | `а теперь по месяцам в Excel` — без хэштега, та же база; через час простоя — заново |
| Большие выгрузки | модель пишет запрос, мост проверяет его в 1С без выполнения, гонит по месяцам и собирает xlsx (фильтры, шапка, настоящие даты и числа) |
| Word и Excel | ответ на письмо, справка, сводная — готовым файлом в чат |
| Фото, PDF, файлы | скриншот ошибки — модель видит картинку; PDF/docx/xlsx читаются вместе с вопросом |
| Поиск по коду 1С | «где это считается», «какая процедура заполняет…» — по индексу выгрузки конфигурации, ответ со ссылкой `путь:строки` ([onec_rag/README.md](onec_rag/README.md)) |
| База знаний | 78 документов из папки «База знаний», поиск с учётом словоформ |
| Пауза | владелец: `/пауза`, `/старт`. Всем: `/базы`, `/новый`, `/помощь` |
| API-мост | `POST /api/ask` — тот же помощник для Langflow и внутренних сервисов |
| Журнал | `python scripts/stats.py` — вопросы, % без ошибок, время, цена, базы |

## Безопасность (базы боевые — агент только читает)

- **Кто может писать:** по умолчанию все сотрудники организации (`allow_all` в `config/users.yaml`); можно ограничить списком UUID — тогда остальным бот молча не отвечает.
- **Только нужные инструменты.** Терминал, файлы и сеть у агента отключены: `--permission-mode dontAsk` + `--disallowedTools`. Мост ещё и сверяет фактический список инструментов в событии `init`; если там лишнее, процесс убивается до первого хода модели.
- **Одна база на вопрос:** MCP-сервер 1С получает только выбранную базу.
- **Агент не видит секретов:** логин и пароль API Коннекта и токены — только у моста, из окружения агента они вырезаются. Агент стартует в пустой папке.
- **Текст из чата — не команда:** вопрос идёт через stdin как данные, в командной строке только фиксированные значения; ответ чистится от путей, имён инструментов и Markdown.
- **Приёмники:** Bearer-токен (сравнение в постоянном времени), дедупликация по `message_id`, эхо сообщений бота игнорируется.

## Запуск на сервере

Один раз, под тем пользователем Windows, под которым выполнен вход в Claude Code:

```powershell
powershell -ExecutionPolicy Bypass -File setup.ps1
```

Скрипт ставит зависимости и cloudflared, создаёт конфиги и `.env`, собирает базу знаний, проверяет Claude (`scripts/check_claude.py`), включает автозапуск при старте сервера (без окна консоли) и запускает бота. Какие доступы вписать в `.env` — в файле «Доступы ИИ-помощника.docx».

Перед запуском на том же сервере должно быть запущено приложение 1С-Коннект, в котором выполнен вход под учёткой «ГК Эксперт | ИИ-помощник». В настройках API кабинета администратора нужно разрешить API.

Дальше всё само (`scripts/start.py`):
- мост подключается к приложению 1С-Коннект и переподключается, если оно перезапустилось;
- упал мост — поднимается заново;
- база знаний переиндексируется сама, когда меняется папка «База знаний»;
- только для `channel: line`: HTTPS-туннель Cloudflare и регистрация вебхука.

Доступ: бот отвечает всем сотрудникам организации (`allow_all: true` в `config/users.yaml`). Кто ставит бота на паузу, пишет боту `/id` и вписывает свой UUID с `owner: true`.

Логи: `logs/start.log`, `logs/bridge.log`. Статистика: `python scripts/stats.py`.

Проверка без Коннекта и подписки: `python -m bridge.cli` — консольный чат (с `claude.binary: "scripts/mock_claude.cmd"` в `settings.yaml` — заглушка CLI).

## Отличия от Telegram-версии

- **Приём через приложение 1С-Коннект**, а не long-polling. Соединение локальное, сервер наружу не торчит, HTTPS не нужен.
- **«Печатает…» нет в API Коннекта** — вместо этого бот сразу отвечает «Принял, работаю над ответом…» (`connect.ack_text`).
- **Rich Messages нет** — ответ простым текстом, таблицы больше 20 строк уходят файлом.
- **Файлы от сотрудника в личном чате бот не получает** — API приложений их не передаёт. Отправлять файлы бот может.

## Боевая база 1С

Базы описываются в `config/bases.yaml`, id — только латиницей. Для боевой базы нужен read-only HTTP-сервис и отдельная учётка только на чтение:

| Метод | Путь | |
|---|---|---|
| GET | `/hs/ai_readonly/metadata[?object=Документ.X]` | состав базы / реквизиты объекта |
| POST | `/hs/ai_readonly/query` `{"query","params","validate_only"}` | выборка; `validate_only` — проверка без выполнения |

Пока HTTP-сервиса нет, работает `mode: mock` на демо-данных.

## Поиск по коду 1С

Память по коду конфигурации — модуль `onec_rag`: индекс выгрузки в одном файле SQLite (FTS5) и MCP-сервер `onec_code` с инструментами `search_1c`, `get_module`, `find_object`. Работает без хэштега базы. Установка одной командой:

```powershell
powershell -ExecutionPolicy Bypass -File onec_rag\install.ps1 -RepoPath "D:\1c-dumps\base" -RepoName base
```

Смысловой поиск (векторы в том же файле, модель на CPU) — тот же скрипт с ключом `-Semantic`. Индекс обновляет Планировщик задач (`git pull` + доиндексация раз в 10 минут), постоянных процессов нет. Подробно — [onec_rag/README.md](onec_rag/README.md). Старый `search_code` (подстрока по `code_dump_dir` выбранной базы) оставлен как запасной.

## Проверка контрагента

`counterparty_check_client.py` — HTTP-сервис 1С `CounterpartyCheck` (POST, Basic Auth, `{"bin": ...}`).
Настройки только из окружения (`COUNTERPARTY_CHECK_URL`, `_LOGIN`, `_PASSWORD`, `_TIMEOUT_SECONDS`); для консоли можно положить их в `.env` (образец — `.env.example`, сам `.env` в `.gitignore`).

```bash
python counterparty_check_client.py 750710450345
```

`check_counterparty(bin, calculation_datetime=None)` возвращает `status`:
- `ok` — обычный сценарий;
- `needs_manager` — долг > 0 или есть неподписанные ЭАВР, передать клиент-менеджеру;
- `error` — проверить не удалось, это не «чистый» контрагент.

Код выхода консоли: 0 / 2 / 1 соответственно. Пароль и `Authorization` вычищаются из логов и текста ошибок.

В боте: если задан `COUNTERPARTY_CHECK_URL`, у агента появляется инструмент `check_counterparty` (сервер `mcp_counterparty`). Сотрудник пишет «проверь контрагента 750710450345» — бот называет долг, неподписанные ЭАВР и решение. Логин и пароль сервер берёт из окружения, которое наследует от `claude`, в MCP-конфиг на диске они не пишутся.

## Тесты

```bash
python -m pytest tests
```

77 тестов. Покрыто:
- весь путь вебхук → очередь → Claude (заглушка) → ответ и файлы в Коннект;
- дубли, эхо бота, чужие пользователи;
- вложение, а потом вопрос к нему;
- пауза, лимит подписки, API-мост, срабатывание защиты от лишних инструментов;
- MCP-серверы по настоящему stdio-протоколу: помесячная выгрузка в xlsx, поиск по коду, Word, вложения;
- поиск по базе знаний;
- поиск по коду 1С: чанкинг, инкрементальный индекс, ранжирование, MCP-сервер по stdio.

**Не проверено здесь:** настоящий Claude Code CLI (на этой машине не установлен), настоящий 1С-Коннект и боевая 1С. Первое проверяет `scripts/check_claude.py`, остальное — первый живой вопрос.
