# Поиск по коду 1С для ИИ-помощника (onec_rag)

Бот отвечает через Claude Code CLI, но Claude не знает код нашей конфигурации. Этот модуль даёт ему память по коду: индекс выгрузки конфигурации в одном файле SQLite и MCP-сервер с тремя инструментами.

```
выгрузка 1С (git) ──(Планировщик задач, раз в 10 мин: git pull + onec_index.py)──▶ .index/onec_code.sqlite3
                                                                                          │ только чтение
сотрудник → бот → Claude Code CLI ──(stdio, на время вопроса)──▶ onec_mcp.py ─────────────┘
```

- Постоянных процессов нет. MCP-сервер запускает сам Claude Code на время вопроса, индекс обновляет Планировщик задач.
- Ничего не уходит наружу: поиск — SQLite FTS5 (`tokenize='trigram'`) на этом же сервере. Нет Qdrant, Postgres, Docker, torch, эмбеддингов.
- Зависимости: стандартная библиотека Python и пакет `mcp`.
- MCP открывает индекс с `mode=ro`; индексатор пишет в WAL-режиме, поэтому бот продолжает отвечать во время переиндексации.

## Файлы

| Файл | Что делает |
|---|---|
| `onec_index.py` | индексатор: обход выгрузки, чанкинг, инкрементальное обновление |
| `onec_mcp.py` | MCP-сервер: `search_1c`, `get_module`, `find_object` |
| `eval.py` | проверка качества поиска: top-1 / top-5 / top-8 |
| `check_bot.py` | один настоящий вопрос через тот же запуск CLI, что у бота |
| `install.ps1`, `install.bat` | установка на Windows: venv, первый прогон, задача в Планировщике |
| `eval_questions.ssl.json` | 35 контрольных вопросов по открытой БСП (см. «Отчёт о проверке») |
| `config.example.json` | образец конфига; рабочий `config.json` в git не попадает |

## Установка на Windows-сервере

Нужны Python 3.10+ и git. Выгрузка конфигурации должна лежать в папке — обычно это рабочая копия git-репозитория, в который выгружают конфигурацию.

```powershell
powershell -ExecutionPolicy Bypass -File onec_rag\install.ps1 -RepoPath "D:\1c-dumps\base" -RepoName base
```

Скрипт создаёт `onec_rag\.venv`, ставит `mcp`, пишет `config.json`, строит индекс и регистрирует задачу `OnecCodeIndex` (каждые 10 минут: `git pull --ff-only` и доиндексация). Повторный запуск безопасен.

То же без PowerShell-окна: `onec_rag\install.bat -RepoPath "D:\1c-dumps\base" -RepoName base`.

Параметры: `-IntervalMinutes 10`, `-NoTask` (не трогать Планировщик), `-CurrentUserOnly` (задача работает только при открытом сеансе пользователя, пароль не спрашивается). Без `-CurrentUserOnly` Windows спросит пароль пользователя: задача должна работать без входа в систему, а `git pull` — видеть его учётные данные git.

Бот подхватывает инструменты сам: мост добавляет сервер `onec_code` в `--mcp-config` и три инструмента в `--allowedTools`, как только появился `onec_rag/config.json`. Перезапуск не нужен — конфиг MCP собирается на каждый вопрос.

Выключить: переименовать или удалить `onec_rag\config.json` — бот продолжит работать без поиска по коду. Это же первое действие, если после установки бот стал отвечать ошибкой: мост останавливает вопрос, когда MCP-сервер не запустился (например, в venv не встал пакет `mcp`).

## Конфиг

Все пути — в `config.json`, в коде путей нет. Относительные пути считаются от папки конфига. Файл можно сохранять в Блокноте (UTF-8 с BOM читается).

```json
{
  "index_path": "../.index/onec_code.sqlite3",
  "log_path": "../logs/onec_index.log",
  "repos": [
    {"name": "base", "path": "D:/1c-dumps/base", "git_pull": true}
  ],
  "search": {
    "default_limit": 8, "max_limit": 20, "max_output_chars": 12000, "candidates": 400,
    "weights": {"path": 3.0, "name": 10.0, "doc": 4.0, "body": 1.0},
    "synonyms": {"пен": ["штраф", "неустойк"]}
  }
}
```

- `repos` — одна или несколько выгрузок. `name` (латиница) — первая часть ссылки: `base/Documents/…:10-40`.
- `weights` — веса bm25 по колонкам: имя процедуры весит в 10 раз больше тела, описание (комментарий над процедурой) — в 4 раза, путь и имя объекта — в 3 раза.
- `candidates` — сколько кандидатов брать из bm25 перед пересортировкой.
- `synonyms` — основа слова из вопроса → подстроки, которые искать в коде дополнительно. Основной способ подтянуть качество без переиндексации.
- Другой конфиг: `--config путь` или переменная `ONEC_RAG_CONFIG`. В `config/settings.yaml` бота — `onec_code.config_path`.

## Запуск и обновление индекса

```powershell
onec_rag\.venv\Scripts\python onec_rag\onec_index.py            # git pull + доиндексация изменённого
onec_rag\.venv\Scripts\python onec_rag\onec_index.py --no-pull  # без git pull
onec_rag\.venv\Scripts\python onec_rag\onec_index.py --full     # перестроить с нуля
onec_rag\.venv\Scripts\python onec_rag\onec_index.py --stats    # размер и состав индекса
```

Изменённые файлы определяются по `mtime` + размеру. Удалённые из выгрузки файлы убираются из индекса. Если каталог выгрузки недоступен, индекс этого репозитория не трогается, код возврата 1. Журнал — `logs/onec_index.log`.

## Что индексируется

- **Модули `*.bsl`** (читаются как `utf-8-sig`). Чанк — процедура или функция от `Процедура`/`Функция`/`Procedure`/`Function` до `КонецПроцедуры`/`КонецФункции`/`EndProcedure`/`EndFunction`, вместе с комментариями `//` и директивами `&НаСервере` над ней. Код вне процедур (переменные, тело модуля) — отдельные чанки. Модуль без процедур — один чанк.
- **Метаданные из пути**: вид объекта (Документ, Справочник, ОбщийМодуль…), имя объекта, вид модуля (МодульОбъекта, МодульМенеджера, МодульФормы + имя формы, МодульКоманды, МодульНабораЗаписей…), имя процедуры, строки начала и конца, признак `Экспорт`.
- **Структура объектов из XML** (Конфигуратор: `Documents/Имя.xml`; EDT: `Documents/Имя/Имя.mdo`): синоним, реквизиты с типами, табличные части, измерения и ресурсы, формы, команды, макеты, движения документа, обработчик подписки и метод регламентного задания. Один чанк на объект.
- В FTS четыре колонки: путь (с русскими названиями вида объекта и модуля), имя процедуры, описание (комментарий над процедурой) и тело.

Ранжирование в два шага. Сначала bm25 с весами колонок отбирает кандидатов четырьмя запросами: OR и AND по всему чанку и OR и AND только по имени с описанием. Потом кандидаты пересортировываются: сколько слов запроса покрыто, где они нашлись (имя > описание > путь > тело), начинается ли с них слово (`рол` в `РолиДоступны` — да, в `Контроль` — нет), сколько слов попало в имя. Точное имя процедуры или объекта из вопроса, экспортные процедуры и — для вопросов про состав объекта — чанки структуры получают надбавку.

Оба формата выгрузки разбираются одними правилами: вид объекта определяется по папке (`Documents`, `Catalogs`, `CommonModules`…), вид модуля — по имени файла.

## Инструменты MCP

| Инструмент | Что возвращает |
|---|---|
| `search_1c(query, limit=8)` | до `limit` чанков: ссылка, объект · модуль · процедура, строки с совпадениями и их номера |
| `get_module(path, procedure="", start_line=0)` | модуль с номерами строк, одну процедуру по имени или часть модуля. Большой модуль отдаётся оглавлением |
| `find_object(name)` | структура объекта и список его модулей. Принимает имя, `Документ.Имя` или синоним |

Каждый результат начинается со ссылки `репозиторий/путь:строки`.

Обработка запроса в `search_1c`: слова разбиваются, стоп-слова («где», «какая», «процедура»…) убираются, у русских слов грубо срезается окончание («заполняет» → `заполн`, «реализации» → `реализац`), слова соединяются через OR. Имена из кода (`ЗначениеРеквизитаОбъекта`, `Модуль.Процедура`) ищутся как есть. Trigram ищет подстроку, поэтому `заполн` находит и `ЗаполнитьТабличнуюЧасть`. Вывод ограничен `max_output_chars`.

`get_module` читает файл с диска, но только тот, что есть в индексе, — произвольный путь прочитать нельзя.

Подключение вне бота (например, в Claude Code разработчика) — `.mcp.json` в папке проекта:

```json
{"mcpServers": {"onec_code": {
  "command": "C:/bot/onec_rag/.venv/Scripts/python.exe",
  "args": ["C:/bot/onec_rag/onec_mcp.py"],
  "env": {"PYTHONUTF8": "1", "ONEC_RAG_CONFIG": "C:/bot/onec_rag/config.json"}
}}}
```

## Как проверять

```powershell
python -m pytest tests\test_onec_rag.py                         # чанкинг, инкрементальность, поиск, MCP по stdio
onec_rag\.venv\Scripts\python onec_rag\eval.py --generate 30    # набрать вопросы из своего кода
onec_rag\.venv\Scripts\python onec_rag\eval.py                  # таблица попаданий и top-1 / top-5 / top-8
python onec_rag\check_bot.py "где считается пеня?"              # настоящий вопрос через CLI бота
```

`eval.py --generate` берёт процедуры с уникальными именами и строит вопросы трёх видов: по комментарию над процедурой, по имени процедуры, разбитому на слова, и «что делает Модуль.Процедура». Это заготовка: такие вопросы легче настоящих, потому что их слова есть в коде. Добавьте в `eval_questions.json` реальные вопросы сотрудников — метрика станет честной. В `expect` — один вариант или список допустимых:

```json
{"q": "где считается пеня", "expect": [{"path": "CommonModules/РасчетПени", "proc": "РассчитатьПеню"}]}
```

`eval.py --min-top8 0.7` возвращает код 1, если top-8 ниже порога.

Если попаданий мало: добавить `synonyms`, поменять `weights`, поднять `candidates` — и перемерить. Переиндексация для этого не нужна.

## Отчёт о проверке

Выгрузку конфигурации заказчик не передал (в присланном архиве — документы базы знаний). Проверка сделана на открытой Библиотеке стандартных подсистем 3.1 (`github.com/1c-syntax/ssl_3_1`, выгрузка Конфигуратора): БСП входит в любую типовую конфигурацию, и вопросы вида «что делает ОбщегоНазначения.…» относятся к ней.

| | |
|---|---|
| Корпус | 2 252 модуля `.bsl` (81 МБ), 1 221 XML объектов |
| Чанков | 41 206: 39 594 процедуры и функции, 1 221 структура объекта, 391 блок кода вне процедур |
| Первый прогон | 15 с |
| Повторный прогон без изменений | 0,8 с |
| Размер индекса | 287 МБ (в 3,5 раза больше исходных `.bsl`) |
| Время одного `search_1c` | 0,2–0,5 с |

Замеры — на ноутбуке с SSD (macOS, Python 3.14); на Windows-сервере цифры будут другими, порядок тот же.

Качество поиска, один запрос без переформулировок:

| Набор вопросов | top-1 | top-5 | top-8 |
|---|---|---|---|
| 35 ручных вопросов «как спрашивает сотрудник» (`eval_questions.ssl.json`) | 46 % | 69 % | 77 % |
| те же вопросы, первая версия поиска (до доработки) | 29 % | 54 % | 57 % |
| 150 сгенерированных из кода (`eval.py --generate 150 --seed 3`) | 90 % | 96 % | 98 % |

Что дало прирост на ручном наборе: отдельная колонка с описанием процедуры, учёт начала слова при пересортировке, надбавка за слова запроса в имени, отдельный отбор кандидатов по имени и описанию.

Восемь ручных вопросов не попали в top-8. В двух поиск вернул первым другой подходящий ответ (`ЗаписатьСобытияВЖурналРегистрации` на «как записать событие в журнал регистрации»), ожидание в наборе строже. В остальных слова вопроса не совпадают со словами кода: «сгенерировать пароль» ↔ `СоздатьПароль`, «заблокировать вход» ↔ `УстановитьБлокировкуСоединений`, «вывести» ↔ «выводит». Это предел лексического поиска; в боте его частично закрывает модель, которая по системному промпту переформулирует запрос 2–3 раза.

Повторить:

```powershell
git clone --depth 1 https://github.com/1c-syntax/ssl_3_1 D:\1c-dumps\ssl
# в config.json: {"name": "ssl", "path": "D:/1c-dumps/ssl/src/cf", "git_pull": false}
onec_rag\.venv\Scripts\python onec_rag\onec_index.py
onec_rag\.venv\Scripts\python onec_rag\eval.py --questions onec_rag\eval_questions.ssl.json
```

Что не проверено:

- **Код заказчика.** Метрики выше — на БСП. На своей конфигурации их нужно перемерить: `eval.py --generate 30`, затем дополнить реальными вопросами.
- **Ответ модели через бота.** CLI с флагами бота запускается, в сессии видны три инструмента `mcp__onec_code__*` и нет лишних, сами инструменты по stdio отвечают. До ответа модели дело не дошло: на машине разработки истёк вход в Claude Code (`401 OAuth access token has expired`). После `claude` → `/login` — `python onec_rag\check_bot.py "вопрос"`.
- **`install.ps1`, `install.bat` и Планировщик задач.** Написаны по документации, на Windows не запускались ни разу.
- **EDT.** Разбор `.mdo` проверен только тестом на образце.

## Допущения

1. **Формат выгрузки** — «Выгрузить конфигурацию в файлы» Конфигуратора или проект EDT. Поддержаны оба. Проверено на выгрузке Конфигуратора (БСП 3.1); разбор `.mdo` EDT проверен только тестом на образце.
2. **Выгрузка лежит в git** и обновляется `git pull --ff-only`. Если git нет — `"git_pull": false`, тогда индексатор просто перечитывает папку.
3. **Код конфигурации один для всех баз**, поэтому инструменты доступны боту всегда, без хэштега базы. Несколько конфигураций — несколько записей в `repos`; в ссылке видно, откуда код.
4. **Конфиг — JSON, а не YAML**: ограничение «только stdlib + mcp».
5. **Свой venv** `onec_rag\.venv` только с пакетом `mcp`. Мост запускает MCP-сервер из него, а если venv нет — своим Python (`settings.python`).
6. **Имя сервера `onec_code`** — латиницей, как остальные серверы бота. Инструменты: `mcp__onec_code__search_1c`, `…get_module`, `…find_object`.
7. **Старый `search_code`** (поиск подстроки по `code_dump_dir` выбранной базы) оставлен как запасной. Системный промпт направляет модель на `search_1c`.
8. **Ссылки на код разрешено показывать сотруднику.** В системном промпте для них сделано исключение из правила «не показывай пути»; относительные пути чистка ответа не трогает.
9. **«ё» сводится к «е»** в индексе и в запросе. В выдаче `search_1c` буква «ё» показана как «е»; `get_module` отдаёт текст как в файле.
10. **`install.ps1` — только ASCII**: Windows PowerShell 5.1 читает UTF-8 без BOM как ANSI и ломает кириллицу.
11. **Длинные пути и кириллица**: файлы открываются через префикс `\\?\`, поэтому `LongPathsEnabled` в реестре не нужен. Для git ставится `core.longpaths=true` и `core.quotepath=false` в репозитории выгрузки. Пути в индексе приведены к NFC.

## Известные ограничения

- Поиск лексический. Вопрос, в котором нет ни одного слова из кода («почему клиенту не дали скидку»), найдёт мало. Частично лечится `synonyms`, полностью — следующим шагом ниже.
- Trigram не ищет слова короче трёх букв: «НДС» находится, «ОС» — нет.
- Стемминг грубый: срезает окончания по списку и не знает чередований («счёт» ↔ «считать»). Самые частые пары заданы синонимами.
- Чанкинг — регулярными выражениями, без разбора языка. Процедура без `КонецПроцедуры` тянется до следующей процедуры.
- Формы (`Form.xml`), права ролей и макеты не индексируются; из формы берётся только модуль.
- Индекс в 3–4 раза больше исходных `.bsl`: FTS хранит текст и триграммы. Для конфигурации с 1 ГБ кода — около 3,5 ГБ.
- `mtime` + размер не замечают правку, сохранившую и то и другое; на такой случай есть `--full`.
- Время запроса растёт с размером конфигурации: на БСП (40 тыс. процедур) — до 0,5 с, на конфигурации в 10 раз больше частые слова («документ», «заполнить») могут дать несколько секунд.
- Редкое слово в вопросе не весит больше частого: «проверка корректности ИНН контрагента» ставит `ИННСоответствуетТребованиям` четвёртым, а не первым.

## Следующий шаг (не сделан, нужно согласие)

Если лексического поиска не хватит по смыслу — добавить в тот же файл SQLite векторный слой: расширение `sqlite-vec` и эмбеддинги через ONNX Runtime на CPU (небольшая многоязычная модель, файл модели лежит локально). Новых сервисов и процессов не появляется, код наружу не уходит; поиск станет гибридным: FTS + векторы, слияние рангов. Цена: зависимости `sqlite-vec`, `onnxruntime`, `tokenizers`, модель на 100–500 МБ, первый прогон на порядок дольше. Решать после `eval.py` на реальных вопросах сотрудников.
